- 現在のブランチは `feature/ai-image-quiz-pool-expansion`。
- 現ワークスペースには `real-or-fake-photo/assets/real/` と既存実写 5 枚、`metadata.json` だけがある。
- `real-or-fake-photo/assets/fake/`、`expression-quiz/`、添付で言及された `make_placeholders.py` は現ワークスペースに存在しない。
- `.agents/ai-image-quiz-games-plan.md` は存在するが未追跡ファイル。既存 5 実写のクレジット、既存 5 偽物の生成プロンプト、既存 3 表情の生成プロンプト、両ゲームの設計が記載されている。
- 添付は旧作業場所 `ykobashi.github.io-worktrees/ai-image-quiz-games` と旧コミットを前提にしているが、最新 AGENTS.md は worktree を使わず現ブランチで作業するよう指定している。添付内の相対リンクも旧 worktree を指すため、そのまま実ファイルパスとして扱えない。

## 実写素材の取得要件

- Openverse API `GET /v1/images/?q=<query>&license=cc0,pdm&page_size=10` を用い、11カテゴリから合計25枚を選ぶ。
- 採用条件:
  - API上のライセンスが `cc0` または `pdm`
  - 幅800px以上を目安
  - 一般向け・AdSense掲載サイトに適した、過激・生々しすぎない内容
  - 既存5枚と同程度の「奇妙だが見られる」トーン
- 保存先と命名は `real-or-fake-photo/assets/real/06_<slug>.jpg` ～ `30_<slug>.jpg`。
- 各素材について最低でも `title` / `creator` / `license` / `source` を保持する。既存 `metadata.json` はさらに `image_url` / `width` / `height` を持つので、新規25件も同形式に揃えるのが安全。
- `.agents/ai-image-quiz-games-plan.md` に既存と同じクレジット表形式で25件を追記する必要がある。

## AI生成画像の要件

### 偽物鑑定

- 新規実写25枚それぞれに、雰囲気・構図・トーンを合わせた架空の生物/物体の日本語プロンプトを1つ作る。
- 保存先は `real-or-fake-photo/assets/fake/06_<slug>.jpg` ～ `30_<slug>.jpg` で、対応する実写と同名。
- `.jpg` へ統一し、長辺1200px程度・JPEG品質80前後が目安。実写/生成画像間で圧縮形式そのものが判別材料にならないようにする。
- 現状は既存1～5の偽物画像も存在しないため、ゲームを実際に成立させるには新規25枚だけでなく `01`～`05` も生成または暫定プレースホルダー化が必要。

### 表情当て

- 添付記載の27プロンプトを内容変更せず使用し、`expression-quiz/assets/faces/pattern-04.jpg` ～ `pattern-30.jpg` として保存する。
- 女性14件・男性13件の指定。顔のクローズアップ、無地背景、線画＋平坦色系の統一スタイル。
- 現状は `expression-quiz` 自体がなく、既存想定の `pattern-a.jpg` ～ `pattern-c.jpg` も存在しない。30件バンクを画像欠損なしで動かすには、この3枚も生成または暫定プレースホルダー化する必要がある。
- 添付中の「平坂色」は通常の表現ではなく「平坦色」または「平塗り」の誤記と思われる。ただし「内容をそのまま追加」と明記されているため、記録用プロンプトは原文維持が安全。画像生成時だけ意図補足を加える場合は、原文を消さず併記する。

## プレースホルダー案

- 添付は画像生成できない場合、既存 `make_placeholders.py` と同方式の「単色＋ラベル」JPEGを許容している。
- ただし当該スクリプトは現ワークスペースにないため、利用するなら新規作成が必要。
- プレースホルダーはファイル欠損を防げる一方、偽物鑑定では単色画像が即座に偽物と分かりゲーム性を失う。正式実装としては AI 画像生成を優先し、プレースホルダーは構造・テスト確認の暫定手段に限定すべき。
- 表情クイズでもラベル入りプレースホルダーは答えや感情を漏らす恐れがある。ラベルには `pattern-04` のような識別子のみを使い、感情名・正解シナリオを含めない。

## 既存資産の構成

```text
real-or-fake-photo/
└─ assets/
   └─ real/
      ├─ 01_ugly-fish-thing-monster.jpg
      ├─ 02_serrivomer-deepsea-fish.jpg
      ├─ 03_jellyfish-background.jpg
      ├─ 04_electric-color-creature.jpg
      ├─ 05_free-jellyfish-image.jpg
      └─ metadata.json
```

- 既存画像のファイルサイズは約123KB～598KB。
- `metadata.json` 記載の元画像幅は1024～4864pxでばらつくため、UI側の固定 `aspect-ratio: 4/3` と `object-fit: cover` は必須。
- 表情画像は `aspect-ratio: 1` と `object-fit: contain` が既存計画の指定。

## 実現上の主なリスク

1. **外部取得の失敗**: Openverse API結果の `url` が期限切れ、配信元が直リンクを拒否、画像形式がJPEG以外、リダイレクトや404という場合がある。ダウンロード後にHTTP成功だけでなく画像デコード、寸法、実ファイル形式を検証する必要がある。
2. **ライセンス・出典の不整合**: APIの検索条件だけに依存せず、採用レコードの `license`、作者、原典URLを保存し、コードの `credit` と `metadata.json` と計画書を一致させる。
3. **不適切素材**: 深海生物、X線、標本系は死骸や医療画像が混ざりやすい。サムネイルまたは実画像の目視確認が必要。
4. **判別バイアス**: AI側だけ解像感、アスペクト比、圧縮ノイズ、背景、彩度が揃いすぎると内容以外で判別できる。各ペアごとに構図・明暗・トリミング・JPEG圧縮を近づける必要がある。
5. **画像生成量**: 現状欠損分を含めると、偽物30枚＋表情30枚の最大60枚が必要。添付が直接要求する追加分だけでも52枚（偽物25＋表情27）であり、一括生成は時間・品質ばらつき・ファイル対応ミスのリスクが高い。
6. **ID/ファイル対応ミス**: `pair-06`～`pair-30`、実写名、偽物名、クレジットの1対1対応を機械検証すべき。表情側も `pattern-04`～`pattern-30` の連番欠落と重複を検査する。
7. **情報漏えい**: 出題中の `alt`、DOM、通信payloadにクレジットや正解シナリオを含めない。ファイル名自体も答えを直接示す語を避けるのが望ましい。
8. **リポジトリ状態の差異**: 添付は両ゲーム実装済み前提だが、現ワークスペースでは実装本体が見当たらない。別作業の成果を誤って上書きせず、親タスク側で現在のブランチに必要な基盤実装が揃うことを確認してから資産パスを確定する必要がある。

## 推奨検証

- 全60画像について存在、JPEGデコード可否、寸法、極端な容量差を自動検査。
- `PAIR_BANK` の全 `realImage` / `fakeImage` と実ファイルの双方向一致を検査。
- `EXPRESSION_BANK` の全 `image` と実ファイルの双方向一致を検査。
- 実写25枚は目視で内容・トリミング・一般向け適合性を確認。
- 偽物30枚は対応実写と並べ、形式的な手掛かりだけで判別できないか目視確認。
- 表情30枚は性別数、スタイル統一、正解を露骨に示す文字や小物がないことを確認。
